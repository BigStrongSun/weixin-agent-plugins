# 运维、适配与验证边界

## 先区分故障层次

1. 模型或自动化未运行：先查任务与模型服务，不能归因于微信发送。
2. 渠道已启用但实际出站失败：查服务端响应、DNS、网络、认证和会话状态。
3. 微信底座能发但抄送缺失：查 cross-channel-notify 的钩子、来源渠道、会话过滤与配置 schema。
4. 消息队列、归档缺档与补发属于业务层，不能用插件状态推断已经补发。

## 自愈补丁约束

- prepare failed / ret=-2 的服务端含义不是官方文档保证；去 token 重试、notifyStart 与渠道重建是历史观测下的处理策略。
- 原补丁目标是 2.4.9。当前安装包信息为 2.4.10，未发现 session-recovery 模块和关键符号。此结论是安装文件检查，不是运行时端到端恢复证据。
- npm 升级/重新安装可能覆盖本地补丁；归档到 GitHub 不会自动给安装包打补丁。
- 渠道热重载可能被活动任务延后；不能把“请求了重载”当作“重载已完成”。
- 60 秒公开版本与 15 分钟本地变体不是一个版本；详见补丁矩阵。

## 验证标准

- 需要新的微信入站、明确的出站结果和用户可见消息证据，才能报告恢复。
- 自动化发送仅 deliveryStatus=sent 计为成功；configured/running、队列入队、恢复日志都不够。
- PR 描述写的测试通过仅为作者记录；GitHub 的 check 状态另查，不能写成已合并或已上线。
- 本仓库只做语法、来源一致性、补丁可解析性、JSON 与链接结构检查，不触发微信实发。

## 安全与部署

不保存真实 notifyTo、notifyAccountId、context_token、扫码材料、accounts 目录、会话数据库或聊天日志。示例配置只使用占位符。

归档的 cross-channel-notify 是历史实现，其内部有通过 CLI 调用 Gateway send 的路径。这次仅保存原代码，不执行、不部署；不能据此绕过当前 OpenClaw 对消息工具、批准或跨渠道发送的限制。后续产品化应先按当前 SDK / 原生消息接口做适配和测试。
